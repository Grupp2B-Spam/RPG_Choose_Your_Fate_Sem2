# StoryPathManager connection contract for RecapManager

Status: RecapManager's implemented consumer requirements; provider agreement is
pending. Share this document and the [canonical protobuf file](../src/main/proto/storypath/v1/story_path.proto)
with the StoryPathManager team. The proto defines the wire schema; this document
defines the behavior needed to use that schema correctly. No second proto copy
is maintained here.

## Connection and ownership

| Item | Contract |
| --- | --- |
| Transport | Unary gRPC over HTTP/2 |
| Caller/client | RecapManager |
| Provider/server | StoryPathManager |
| Protobuf package | `choose_your_fate.storypath.v1` |
| Service | `StoryPathService` |
| Method | `GetChoicesAfter` |
| Full RPC path | `/choose_your_fate.storypath.v1.StoryPathService/GetChoicesAfter` |
| Authentication | Metadata `authorization: Bearer <access-token>` |
| Data owner | StoryPathManager owns the original journey choices and their sequence |
| Checkpoint owner | RecapManager stores the last included sequence with each character/narrative format |

RecapManager initiates the request. StoryPathManager returns the requested data;
it does not push it to a gRPC server in RecapManager. This read does not use
RabbitMQ. RecapManager's speech publication is a separate connection.

Providers may change `java_package` for their own project. The protobuf package,
service, method, message names, field numbers and types must match the canonical
proto. Do not copy generated Java sources between projects; generate them from
the proto using each service's build.

## Data RecapManager sends

`GetChoicesAfterRequest`:

| Field | Proto type / number | Meaning |
| --- | --- | --- |
| `character_id` | `int32`, 1 | Positive ID of the character whose actual journey is requested |
| `after_sequence` | `int64`, 2 | Exclusive saved checkpoint; `0` means no choices have been summarized yet |
| `page_size` | `int32`, 3 | Positive maximum number of choices in this response; currently defaults to `100` |
| `snapshot_sequence` | `int64`, 4 | `0` starts a new read and captures the current highest journey sequence; later pages echo the first response's value |

The request does not contain the saved summary, a player-selected voice, or a
request to mark data as consumed. RecapManager combines returned choices with its
own saved summary.

## Data StoryPathManager returns

`GetChoicesAfterResponse`:

| Field | Proto type / number | Meaning |
| --- | --- | --- |
| `character_id` | `int32`, 1 | Must equal the requested character ID |
| `snapshot_sequence` | `int64`, 2 | Fixed high-water mark for this read, never below the request's checkpoint |
| `choices` | repeated `PathChoice`, 3 | At most `page_size` choices, in strictly ascending sequence order |
| `has_more` | `bool`, 4 | Whether another page is needed to reach the same high-water mark |

Each `PathChoice` contains:

| Field | Proto type / number | Required behavior |
| --- | --- | --- |
| `sequence` | `int64`, 1 | Positive, stable journey event sequence for this character; strictly greater than the page's `after_sequence` and at most `snapshot_sequence` |
| `choice_id` | `int32`, 2 | Positive ID of the choice that was actually made; never use it as a cursor |
| `from_scene` | `string`, 3 | Source scene label; empty string is accepted if unavailable |
| `to_scene` | `string`, 4 | Destination scene label; empty string is accepted if unavailable |
| `description` | `string`, 5 | Non-blank description of the actual choice/event, used as narrative input |
| `consequence` | `string`, 6 | Resulting consequence when supplied; otherwise empty string |
| `story_weight` | `int32`, 7 | Relative narrative importance; current consumer accepts the full int32 range, including zero |

Only choices actually made belong in the response, not a scene's available
options or summaries generated by another service. Current fixtures use weights
such as `5` and `8`; those values do not define an agreed scale. Character
biography, stats, flags, audio and pre-generated summaries are not required by
this contract.

## Incremental reads and snapshot rules

1. RecapManager reads its saved checkpoint and starts with `snapshot_sequence=0`.
2. StoryPathManager captures the latest committed journey sequence and returns
   only `after_sequence < sequence <= snapshot_sequence`.
3. If `has_more=true`, RecapManager sends another request with `after_sequence`
   set to the last returned sequence and echoes the captured snapshot.
4. Every later response must preserve that snapshot. Choices created after it
   are left for the next complete read, even if they arrive during pagination.
5. A page with `has_more=true` must contain at least one choice and must stop
   before the snapshot. The final page must end exactly at the snapshot.
6. If nothing is newer than the checkpoint, return `choices=[]`, `has_more=false`
   and `snapshot_sequence=after_sequence`. For an initially empty journey, all
   sequence values are `0`. An empty page must not hide a later unreturned choice.

Sequences may have gaps; the consumer does not require consecutive integers.
They must not reset, change meaning, or acquire late backfilled events at/below
an already exposed checkpoint. Two occurrences of the same choice ID must have
different journey sequences. Preserve entries needed for incremental reads; if
history/checkpoints can expire, agree an explicit recovery contract first.

Reads must not delete choices, mark them globally consumed, or advance a
provider-side cursor. Different narrative formats can have different checkpoints,
and a failed RecapManager update must be able to read the same range again.
Repeating the same request against an unchanged snapshot returns the same ordered
data. A newly started read may capture a newer snapshot.

## Request/response examples

These are readable ProtoJSON representations of gRPC messages, not REST routes.
The [ProtoJSON format](https://protobuf.dev/programming-guides/json/) uses camelCase
field names; int64 values are represented as strings.

Character 1 already has choices through sequence 2 summarized. To demonstrate
pagination, this example uses a page size of 1. The current journey ends at 4.

First request:

```json
{
  "characterId": 1,
  "afterSequence": "2",
  "pageSize": 1,
  "snapshotSequence": "0"
}
```

First response:

```json
{
  "characterId": 1,
  "snapshotSequence": "4",
  "choices": [
    {
      "sequence": "3",
      "choiceId": 12,
      "fromScene": "Old bridge",
      "toScene": "Ruined tower",
      "description": "The hero discovered a ruined tower beyond the bridge.",
      "consequence": "A hidden entrance was revealed.",
      "storyWeight": 5
    }
  ],
  "hasMore": true
}
```

Second request:

```json
{
  "characterId": 1,
  "afterSequence": "3",
  "pageSize": 1,
  "snapshotSequence": "4"
}
```

Final response:

```json
{
  "characterId": 1,
  "snapshotSequence": "4",
  "choices": [
    {
      "sequence": "4",
      "choiceId": 13,
      "fromScene": "Ruined tower",
      "toScene": "Tower cellar",
      "description": "The hero explored the hidden cellar.",
      "consequence": "",
      "storyWeight": 8
    }
  ],
  "hasMore": false
}
```

If sequence 5 is committed while these pages are being fetched, it must not
appear in this snapshot. After a successful save, RecapManager's next read starts
after 4 with snapshot 0 and can retrieve sequence 5.

If no sequence 5 exists, a new request after 4 instead receives:

```json
{
  "characterId": 1,
  "snapshotSequence": "4",
  "choices": [],
  "hasMore": false
}
```

## JWT, transport and failures

RecapManager forwards the authenticated HTTP caller's access token on **every**
gRPC page, using lowercase metadata key `authorization` and value
`Bearer <access-token>`. The token is not a protobuf field. StoryPathManager must
validate its trusted issuer, signature, expiry and intended audience and enforce
access to the requested character. RecapManager also performs its own character
access check; it is not a replacement for the provider's authorization.

TLS is the client's default for real StoryPath connections. This contract does
not assign a provider port, Keycloak realm/client, certificate, audience or role
mapping on behalf of the other team. RecapManager's current target defaults are
`localhost:9091` for a host client and `storypath-manager:9091` in its Compose
file; these are client configuration assumptions to confirm, not infrastructure
created by RecapManager. The integration remains mocked until that agreement.

| gRPC outcome | Required interpretation by the provider/client boundary |
| --- | --- |
| `OK` with empty history | Valid request for an existing character with no newer choices |
| `UNAUTHENTICATED` | Missing, expired or invalid token; RecapManager propagates an authentication failure (HTTP 401) |
| `PERMISSION_DENIED` | Valid identity without character access; RecapManager propagates access denial (HTTP 403) |
| `UNAVAILABLE` / `DEADLINE_EXCEEDED` | History retrieval failed; never substitute an empty success |

Proposed provider status choices to confirm: `INVALID_ARGUMENT` for malformed
IDs/cursors/page sizes, `NOT_FOUND` for a nonexistent character (distinct from an
existing character with an empty journey), and `FAILED_PRECONDITION` for a
checkpoint/snapshot that cannot be served consistently. The current client maps
all non-authentication RPC failures, including those proposed statuses, to a
history failure (HTTP 503); it does not implement special HTTP 400/404 mappings.

The current defaults are a 3000 ms deadline **per page**, a page size of 100,
at most 100 pages and AI generation batches of 100 entries. These limits belong
to RecapManager and are configurable. The provider must not silently discard
remaining choices to satisfy a limit. The client rejects replayed/unordered
entries, wrong characters, changing snapshots, oversized pages, pagination with
no progress, and a final page that stops before the captured high-water mark.

## What RecapManager does after the read

All pages are fetched before generation. With new choices, the existing AI tools
combine them with the saved narrative. Only after every generation batch succeeds
does RecapManager save the combined narrative and new checkpoint in one
transaction. Saving a PATH_SUMMARY also records its RabbitMQ publication intent.
No successful save means no checkpoint advance. An empty successful read returns
the saved narrative without a model call, summary update or new publication.

See [the client](../src/main/java/dk/ek/gruppe2/recapmanager/storypath/GrpcJourneyHistoryClient.java)
for the actual validation and JWT forwarding, and
[existing connection tests](../src/test/java/dk/ek/gruppe2/recapmanager/connection/StoryPathClientCT.java)
for executable examples. Those tests use an in-process provider substitute; they
do not prove a connection to the other team's running service.

## Handoff checklist for the StoryPathManager team

- Confirm this proto and snapshot/checkpoint semantics, including recovery if
  their journey data can be edited, removed or expire.
- Confirm the server address/port, TLS setup, JWT trust/audience and authorization
  behavior; shared caller-token acceptance is required by the current client.
- Agree the relative weight scale, scene label meaning and proposed error statuses.
- Verify first read, multiple pages, concurrent new choices, no additions,
  repeated reads and denied/expired tokens against their implementation.
- Once agreed, enable the existing real client with `app.storypath.mode=grpc`
  and the agreed target/security configuration. No StoryPathManager service or
  database is implemented or changed by this handoff.
